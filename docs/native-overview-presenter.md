# 完整总览的原生宿主适配

这是上一轮[原生宿主实验](live-overview-surface.md)的生产结构适配，仍需显式启用。默认启动保留 WinForms 顶层窗口，新路径使用真实 WPF 顶层窗口；两者复用同一个 `SpatialOverviewView`，地图、搜索、工作区和 CRT 内容不再分别实现。

## 使用与边界

试用包的 `Start.cmd` 继续启动默认路径。要验证新路径，先从托盘“退出并恢复窗口”，再双击 `Start-NativeOverview.cmd`；也可以运行：

```powershell
./BorderlessFlatWindow.App.exe --native-overview
```

它接入现有管理器、画布会话、全局快捷键、选窗和恢复流程。`--native-overview-solid` 可强制纯色降级。Windows 11 build 22621 起可请求系统 Desktop Acrylic；系统不支持或高对比度时使用纯色。接口成功仍不证明实际背景视觉符合要求，不修改系统透明度设置。

这里尚未将原生路径设为默认，也没有完成真实连续呈现、自然操作、混合 DPI 或全部兼容验收。最初工具画面中背景仍呈纯色，后续[背景配置修正与合成验证](native-backdrop-validation.md)已定位并解决本机非客户区渲染策略问题；下文保留适配初轮的证据。目标是保留空间关系并减少同步桌面读回，不能以降低总览功能或静态卡片列表替代需求。

## 结构与所有权

- `SpatialOverviewView` 是可直接放入 WPF 窗口的视图，负责布局、空间投影、搜索、工作区、输入命令和唯一 WPF 动画值。
- `SpatialOverviewScene` 是保留原 API 的薄 `ElementHost` 适配器。默认窗体继续使用它；重复释放不会再次访问已销毁的 ElementHost 内部对象。
- `IOverviewPresenter` 是管理器与具体宿主之间的边界。`FormOverviewPresenter` 包装已有窗体，`NativeOverviewPresenter` 使用 `SpatialOverviewWindow`。接口的 Handle、Visible、Closed 都对应实际显示的顶层窗口，没有隐藏或覆盖 Form 属性来伪装宿主。
- 空闲缓存继续保存一个尚未使用的 presenter，沿用完整输入快照、重入代号和单次转移。原生隐藏准备不激活、不绑定外部预览、不读取桌面；背景接口和布局可以提前准备。后续实际打开才重新提供、核验源并注册预览。启动时原生路径只预热共享视图，不创建旧 ElementHost 场景。

新路径的 `PreparePresentation` 不调用屏幕读回或焦点位图裁剪。它将现有地图及工作区切片绑定到实际 WPF HWND 的 DWM 预览；选中源只有在身份、位置和遮挡核验满足条件时才请求原生矩形过渡，否则淡入地图。它不会重新构造源窗口上方的叠加层。离屏内容仍可能停帧。

全局输入继续以会话编号隔离晚到事件，Shown/Activated 提供真实 HWND；原有资源管理器焦点回落兜底继续作用于这个 HWND。选窗确认立即关闭、交接相机与焦点。Tab 切换可以反向；到端点停止 Rendering 订阅，DWM 内容关系独立刷新。外部暂停或管理器取消会直接释放宿主。

工作区编辑使用以真实 HWND 为 owner 的 WinForms 模态框，期间保留模态深度和原生禁用检查；关闭前先释放场景事件、预览和菜单，再通知管理器完成，避免焦点/COM 回调重入旧会话。

## 验证

```powershell
./scripts/check.ps1 -Configuration Release -SmokeUi -NativeChecks -NativeOverviewChecks
```

本轮通过 309 项原有模型/存储/原生检查、默认 UI/场景检查，以及新增验证：

- 1920×1080、3440×1440、960×720，原生背景请求与强制纯色两组，共六个实际 presenter 样本。在真实 WinForms 消息循环中验证隐藏预热无激活/零预览、地图及工作区真实预览、往返及端点空闲后的重新反向、搜索空结果不确认、轮选确认、一次关闭与预览释放。
- 交互样式隐藏 WPF 宿主的三尺寸检查；取消准备后不显示、完成仅一次；重复 Dispose。
- 显式关闭动画时直接完整显示、零动画回调，切换关闭立即释放；系统动画关闭时也不把无回调误判为测试超时。
- 独立视图在合成 100% / 125% / 200% DPI 下的物理预览范围和 1600×1200 图像尺寸。它不是实际混合 DPI 显示器验收。
- 自有 WinForms 模态框中，仅向夹具自身子 HWND 投递 Tab / Esc 消息，验证实际模态消息循环切换控件、取消、宿主禁用与重新启用。它不覆盖硬件输入或全部输入法。
- 首次入口和后续反向分别记录时间；后续 Tab 不会覆盖首次请求，使入口字段错误变为 0。缺失计时写 null，不解释为零延迟。

真实管理器只接管自有 Probe，关闭自动接入。已观察实时地图与工作区背景、地图点选 Source、快捷键重开、Tab 返回；正常暂停后待恢复/armed 均为零。另一次打开工作区保存框后，桌面工具能读取该嵌入模态框却不能把输入定向到它，因此没有声称实际保存/取消的自然操作已通过。该次严格核对唯一源为自有 Probe 后结束测试管理器，独立恢复程序核验原位置与显示状态并清零；没有接管其他应用。

真实自有源的两次显示阶段约为 63.7 / 19.5ms、准备阶段约为 19.5 / 2.8ms；首个样本入口到首回调约 156.9ms。第二个样本的旧入口计时受上述覆盖问题影响，不引用其入口值。顺序、冷/热状态、源位置与工具操作都有影响，这不是与默认路径的随机对照，也不证明提速或屏幕实际呈现。两次焦点变换均因资格不满足而降级，不能据此验收真实窗口的缩小效果。

可选匿名指标保留 renderer、背景 HRESULT、尺寸、计数和阶段耗时，不包含窗口标题、输入内容、身份或桌面像素。原始本地状态、工具画面和报告不提交仓库。默认 CI 只编译这些桌面代码；原生宿主检查需显式在可交互桌面运行。

## 减少重复预览同步

背景修正之后，实机匿名记录暴露出单源会话仍有 80 / 88 次预览同步。检查发现两处重复工作：隐藏准备尚未完成时，布局事件已开始同步中间几何；管理器反复提供相同窗口快照时，原生 presenter 仍无条件同步。这里优化原生路径，默认 WinForms 路径保持原有行为。

现在先完成隐藏布局，再一次性建立原生关系。后续几何通知只比较完整的预览请求，包括身份、物理矩形、裁剪、资格及顺序；请求未变化时不进入原生批次。它缓存的是布局请求，不缓存窗口身份、可见性或桌面归属的核验结果。源快照或可用性变化、源元数据变化、预览开关和 F5 显式重试仍强制运行原有验证。原生调用中发生的刷新请求会在当前批次之后排队处理，关闭后直接失效，避免丢失嵌套更新或递归查询。

新增回归先在旧实现复现准备阶段重复同步 3 次，修正后为 1 次。20 次相同快照不增加同步；标题变化、搜索及恢复、F5、预览开关和暂停/恢复仍生效。测试包装实际 DWM 适配器，在批次内触发自有模型更新：最大批次深度为 1，排队后恰好多一次核验；排队后关闭则不再进入批次。原有多尺寸、双背景、反向、模态输入、DPI 和释放回归继续保留。

可选匿名计时新增 `PreviewLayoutMs`、`PreviewSyncMs`、`PreviewGeometrySkips` 和 `AnimationWorkP95Ms` / `AnimationWorkMaxMs`；没有动画样本时工作耗时写 null。动画工作耗时只覆盖 presenter 回调内进度记账及原生预览更新，位于测试观察回调之前，不是 WPF 渲染、DWM/GPU 呈现或输入延迟。

真实管理器关闭自动接入，只管理一个自有 Source，两次会话共有两个预览关系。第一轮有两次搜索变化，共同步 3 次；第二轮无搜索变化，只同步 1 次。地图及 CRT 内容持续更新，清空搜索恢复预览，点选源、重开、Shift+Tab 返回和暂停恢复通过，待恢复/armed 为零。两轮回调工作 P95 约 0.175 / 0.153ms，首次入口至首回调约 190.7 / 62.5ms，Show 约 78.6 / 20.3ms；这些独立样本受冷/热状态、持续时间与工具影响，不能与先前样本作随机对照。它们支持减少重复查询的结论，也显示首次显示等待仍在，不能据此认定连续动画已经流畅或推断多窗口表现。

## 显示阶段与截图前等待

生产交接现在由 `RequiresDesktopSnapshot` 声明是否需要桌面快照。默认交互式窗体仍在隐藏可见面板后调用 `DwmFlush`，随后读取背景；原生 presenter 不读取桌面位图，因此跳过这项等待。合成验证窗体本身不采集桌面，也不需要该等待。[微软文档](https://learn.microsoft.com/en-us/windows/win32/api/dwmapi/nf-dwmapi-dwmflush)说明 `DwmFlush` 会阻塞调用者，但不刷新整个会话的渲染批次；这里没有把它当作所有第三方内容均已呈现的保证。

匿名指标增加 `DesktopFlushMs`，属于 `HostHideMs` 内部阶段。原生窗口在显式开启计时时进一步拆分 `WindowShowCallMs`、`PostShowLayoutMs`、`ShownNotificationMs` 和 `ActivateCallMs`，分别记录 WPF Show 调用、后置布局、显示通知与显式激活请求。没有执行或尚未完成的阶段保留 null，隐藏准备不产生显示计时；这些值仍不是屏幕呈现延迟，不能与包含它们的 HostShow 重复相加。

自有 Source 的开发态首轮记录：隐藏阶段约 19.7ms，其中桌面同步约 7.8ms；Show 约 105.1ms，其中 WPF Show 调用约 96.2ms、通知约 7.9ms。跳过等待后的独立首轮原生记录：`DesktopFlushMs=null`，隐藏约 11.0ms；Show 约 115.6ms，其中 WPF Show 约 106.6ms，入口至首回调约 222.8ms。两轮间有系统调度和冷启动变化，整体响应没有改善证据；已确认消除了不需要的同步，但主要显示成本仍在。默认路径实机复核同步约 7.7ms，背景采集成功。两个后续会话的实时地图/CRT、Tab 或 Shift+Tab 返回、暂停恢复均通过，待恢复/armed 为零。

## 系统过渡对照

为排查系统窗口过渡是否造成等待，开发者可显式运行下面的自有窗口对照，使用尚不存在的报告路径：

```powershell
./scripts/build.ps1 -Configuration Release
./src/BorderlessFlatWindow.App/bin/Release/net10.0-windows/BorderlessFlatWindow.App.exe --native-overview-check artifacts/native-show-new.json --compare-system-transitions
```

这项额外检查在三个窗口尺寸、两种背景请求下，分别按启用/禁用/禁用/启用顺序设置 `DWMWA_TRANSITIONS_FORCEDISABLED`，共 24 个实际完整 presenter 样本。只操作自身 HWND，不修改系统动画设置；沿用地图/工作区真实预览、反向、空闲、搜索、模态、关闭与资源断言，不采集桌面或请求激活。额外模式的看门狗随四倍样本量从 30 秒扩为 120 秒；普通六样本检查不变。[窗口属性文档](https://learn.microsoft.com/en-us/windows/win32/api/dwmapi/ne-dwmapi-dwmwindowattribute)说明该开关控制单个窗口的 DWM 过渡，设置成功不等于测得其实际画面。

本机 24 次设置均成功，各样本前台不变、预览释放及原有断言通过。下表为每组两个样本的 WPF Show 调用算术均值，单位 ms；它是未激活的自有夹具，不能直接外推到用户桌面激活路径或其他设备。

| 窗口尺寸 | 背景请求 | 系统过渡启用 | 系统过渡禁用 |
| --- | --- | ---: | ---: |
| 1920×1080 | 原生 | 45.7 | 70.5 |
| 1920×1080 | 纯色 | 50.1 | 29.6 |
| 3440×1440 | 原生 | 46.2 | 50.7 |
| 3440×1440 | 纯色 | 49.7 | 68.8 |
| 960×720 | 原生 | 52.6 | 57.1 |
| 960×720 | 纯色 | 51.3 | 46.8 |

差异没有一致方向，样本少且仍受缓存和调度影响，不能支持把禁用系统过渡作为生产优化。生产窗口保持现有系统过渡策略，此开关只存在于显式对照检查。原始报告和工具画面不提交仓库。
